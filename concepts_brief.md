# ContextGuru: Cross-Agent Context Handoff

* **Author:** rnair86
* **Date:** 2026-11-19

## Overview

ContextGuru is a local MCP server written in C# (.NET) that lets a developer save a short handoff of their current work in one coding agent and pick it up later in the same agent or a different one. Target agents are Claude Code, Codex and Cursor. Data is stored in a local SQLite file shared by all agents.

Today the developer shares context between agents by writing a markdown file by hand. The goal is one command per action, with contexts scoped to the project so "latest" means the latest for the repo you are in.

Commands (thin per-agent command files that call the MCP tools):

* `/cg-save-context [name]` - the agent writes a fixed-template handoff and saves it. No name means an auto-generated key. Saving an existing name overwrites it.
* `/cg-get-context [name]` - no name returns the latest for the current project. Shows a brief summary. If there are next steps, asks whether to continue; otherwise waits.
* `/cg-list-contexts` - lists saved contexts for the current project.
* `/cg-remove-context {name}` - deletes one context. Deletion is manual only.

The handoff template has: one-line summary, goal, what was done, decisions, open tasks, next steps. Diffs and file contents are excluded because git holds them. Secrets are handled only by an instruction in the template.

## Analysis

**Constraints the reviewers found**

* **Project identity is the weakest part.** A stdio MCP server only knows the folder it was started in. MCP has no standard field for the client's working folder, and support for the roots list varies by client. If the server guesses wrong, a save in one agent and a get in another can report "no context found". Edge cases: git worktrees, submodules, monorepos, symlinks, Windows drive-letter case, WSL paths (`/mnt/c/...`) versus Windows paths, moved folders, one repo at two paths.
* **The server cannot read the agent's context.** "Save the current context" means the agent writes text and passes it in. The quality of the handoff depends on the template text, which does not exist yet.
* **"Seamless and agent agnostic" is true for the server and not for the commands.** Each agent defines commands differently. Three hand-written command files will drift apart. Codex's current invocation form is unverified (historically `/prompts:` prefix). The `/cg-` prefix avoids the colon that Claude Code reserves for plugin names.
* **Behavior such as "ask about next steps, otherwise wait" is agent conduct, not server logic.** To be consistent across agents, the server's get response should carry the instruction text, and the stored handoff should be marked as data, not instructions, since one agent's text is read by another.
* **Silent overwrite loses data.** Reused names ("wip") and colliding auto-names overwrite earlier work without notice. Adding versions later forces a schema migration.
* **Secrets protected only by a prompt instruction is a stated, accepted risk.** The database file should at least be readable only by the user.
* **Several server processes (one per agent) share one SQLite file.** This needs a schema version, WAL mode, a busy timeout and atomic upsert.
* **Failures are invisible.** Each client starts the server and shows only "MCP server failed". Logs must go to stderr and a file, never stdout, and a diagnostic mode should print the resolved project and database path.

**Scope challenge**

The real gain over the markdown file is one command per action and project scoping. Cheaper alternatives:

* (A) No server: command files plus a `~/.contextguru/<project>/<name>.md` folder.
* (B) An MCP server on plain files, using file modification time for "latest".

SQLite is justified mainly by atomic upsert, indexed latest lookup and listing. The cheapest test is to run the command files and template against a plain markdown folder for a week in all three agents, and build the server only if scoping, listing or atomicity cause problems. The template text is the real product and should be written and hand-tested before any C# is written.

**Inventive contradictions and resolutions**

* Scope by working folder, but the server cannot see it: the agent supplies the project path as a required argument, and the server derives identity and reports how it was derived.
* Same commands everywhere, but per-agent forms differ: the server is the single source of behavior, and command files are generated by an install command rather than hand-written.
* Consistent template, but agents write freely: the server owns the template, validates the shape and returns fix-it errors.
* Simple overwrite, but versions wanted later: keep one previous version (or an append-only revision table) from day one, while the user still sees overwrite semantics.
* Manual-only deletes, but unbounded growth: exact-name remove, with the command file asking you to confirm. No auto-expiry.

**Ideal Final Result**

One command in any agent, and the next agent picks up with no re-explaining. The server, not the agent, derives a stable project identity and flags ambiguity, enforces the template, keeps one prior version, and tells the agent how to present the result. One install command registers the server and writes the command files for all three agents.

**Open facts not verified (no reviewer had web access)**

* Whether Claude Code, Cursor and Codex support the roots list, and what working folder each uses when spawning the server.
* Codex's current command mechanism and argument syntax; Cursor command file frontmatter and argument support.
* Current `ModelContextProtocol` NuGet package version and API.
* Native SQLite on every platform (Linux musl and arm); NativeAOT compatibility.
* Whether `D:\Projects\ContextGuru` is a git repo (reviewers disagreed with the environment header).

## Goals vs. Non-Goals

* **In-Scope Goals:**
  * Local stdio MCP server in C# (.NET), cross-platform (Windows, Linux, Mac), SQLite storage.
  * Four tools: save, get, list, remove.
  * Project-scoped contexts, keyed by project path (folder name and absolute path stored).
  * Fixed-template handoff with a one-line summary.
  * `/cg-` command files for Claude Code, Codex and Cursor, with the Codex form verified.
  * Per-user database location, schema version, WAL mode, diagnostic mode.
  * Size caps on the handoff so get does not flood the next agent's context window.
* **Out-of-Scope Non-Goals:**
  * Dashboard (later).
  * Diffs and file contents in the handoff.
  * Automatic expiry or deletion.
  * Server-side secret scanning (template instruction only, risk accepted).
  * Full version history UI (one prior version kept at most).
  * WSL path mapping (v1 assumes all agents run natively on Windows).
  * Remote or multi-user sync.

## Alternatives Weighed

* **Plain-text only, no MCP server (command files plus a markdown folder).** Not chosen by author: the goal is a shared, project-scoped store across agents. Kept as a one-week validation step for the template.
* **MCP server on plain files instead of SQLite.** Not rejected; cheaper, but loses atomic upsert and indexed listing. Open decision.
* **Remote Git URL as project key.** Rejected by author: not all projects are hosted remotely. Kept as an optional alias column.
* **`/cg:` command prefix.** Replaced by `/cg-` because the colon is reserved for Claude Code plugin names and would not be uniform across agents.
* **Free-form or light-template handoff.** Rejected by author in favor of a fixed template for consistency across agents.
* **Server-side secret scanning.** Rejected by author for v1: template instruction only.
* **Pure overwrite with no history.** Rejected by author: keep one previous version instead, to avoid a schema migration later.
* **Full revision history.** Rejected by author for v1: more tables and a need to prune.
* **Structured template fields.** Rejected by author: markdown body with required headings is simpler and costs fewer tokens.
* **Self-contained executable.** Rejected by author for v1 in favor of a dotnet tool.

## Key Decisions & Staging for Next Steps

**Decided by the author**

* Project scope by repo path (git root, else current folder); store folder name and absolute path.
* Auto-generated keys; overwrite on a repeat name; latest per project on get.
* Fixed template; get shows a brief summary, then asks about next steps if any, otherwise waits.
* Four commands including list and remove; deletes manual.
* `/cg-` prefix; secrets by template instruction only.

* After the Goldfish review: validate the template first. Hand-test the template and command files against a plain markdown folder in all three agents for about a week, then decide whether the server is needed and which design questions below matter.

* Project path: tools take a projectPath argument filled by the command. If it is missing, the server falls back to the MCP roots list, then its own working folder. The response states which source it used. The server normalizes the path (git root, real path, case folding on Windows).
* WSL: not supported in v1. All three agents run natively on Windows. Revisit if that changes.
* Template form: one markdown body with required headings. The server checks the headings and size caps, and returns a clear error naming the missing part.
* Overwrite: keep one previous version. The save result says it overwrote and shows the old timestamp and summary.
* Distribution: dotnet tool (needs the .NET runtime on each machine).

**To settle before the design document**

1. Result of the template validation week (what worked, what hurt: scoping, listing, overwrite).
2. Spike: a trivial server that reports its working folder and roots list, run in all three agents. Record each agent's real command mechanism and the Codex command form.
3. Size caps for the handoff and the exact required headings.
4. How the install step writes command files for each agent (generated by a command, not hand-written).
